   "再引入一套编码"会让 K1 的"全项目唯一退出码语义"失效。K1 因此在 M6 **未变更**。
3. **`bench/last_run.json` 不进源码包**：它是运行产物（每次整矩阵运行都重写）。这与
   `bench.gen.RUNTIME_PRODUCTS` 的放行口径**方向相反但理由一致**——`--check` 放行它是为了不把
   运行产物当生成物，`MANIFEST.in` 排除它是为了包里只放源码。两处都由测试钉住。
4. **sdist 先 `git archive` 导出受控树再构建**：工作树里的未跟踪产物（本机实测：`*.egg-info`）
   不该进发布包。发布包必须由**受版本控制的内容**构成，这是"附件与 tag 树逐字节同源"的前提。

**M6 的「等价」缺口（写清，不笼统）**：

1. **远端面全部未执行**：仓库公开性 / tag 指向 / CI 逐 job / 附件下载复算 sha256，四件都还是
   "门写好了但没喂过真世界"。`--online` 的六条检查目前只经过变异验证（注入坏世界），
   **没有一次真实 gh 调用的成功记录**。
2. **干净 venv / 干净 clone 的 M5 结论沿用**：M6 未重跑"新 venv + `pip install -e .[dev]`"与
   `git clone --no-local` 全流程；C10 的"解包即用"用的是**解包 + PYTHONPATH** 的模块通路，
   不是独立安装。
3. **跨平台逐字节一致仍未实测**：与 M5 同一条边界。
4. **`--online` 的 `check_push_runs_reconciled` 依赖"仓库只有一个 workflow"**：本仓当前确实只有
   `ci.yml`；将来加第二个 workflow 时这条判据会按 `len(workflows)` 自动收紧，但**未在双 workflow
   情形下实测过**。
