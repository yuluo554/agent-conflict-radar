# 项目题：多 agent 并行开发冲突雷达（agent-conflict-radar·按 worktree/会话/文件/函数符号四级粒度预判并行写入冲突·纯本地零上传）

> **性质**：自拟项目题（**不参赛**，成果发布 GitHub **公开仓库**，署名 `yuluo554`）。交付形态为**纯本地 Python CLI**——读取本机 agent 会话与 git/worktree 状态，无 LLM、无 GPU、无服务器、零上传。
> **目标产出**：GitHub 公开仓库（本地目录 `10-18-agent-conflict-radar`，`10-18` 为 2026-10-18 日期标签；GitHub 仓库名发布时用纯净名 `agent-conflict-radar`，沿用惯例 `yuluo554/<kebab-name>`，署名 `yuluo554`）。
> **题目定稿日期**：2026-10-17
> **题目版本**：v1（首版定稿）
> **定位宣言**：**多个 agent 并行改同一个仓库时，冲突往往在合并那一刻才暴露——而那时一个 agent 已经悄悄覆盖了另一个的工作。本工具在写入发生前预警：按 worktree/会话/文件/函数符号四个粒度比对"谁正在改什么"，给出即将冲突的清单。差异化只能押符号级：文件级冲突已有一堆低星工具，函数级与"会话正在进行中"的实时比对仍是空的。**
>
> **独特性拷问（AI 时代必答题）**：LLM 聊天为什么做不到？——它看不到你本机**多个并行会话的实时写入意图**，也无法把"谁正在改哪个文件、哪个函数、哪几行"与 **git worktree 拓扑**对齐成一份可复算的冲突矩阵。本工具的独特性落在三处：①**跨会话的本地持久状态**（Claude Code / Codex 会话日志 + 未提交 diff + worktree 列表）；②**在写入前而非合并后给出判定**（`git merge-tree` 无副作用试合并 + AST 符号区间比对）；③**可复现测量基建**（程序化合成并行场景 + 植入真值，断言检出集合精确匹配）。它不是又一个"合并冲突提示器"，而是把"即将发生的覆盖"提前到可处置的时间点。

## 一、项目介绍

### 1.1 痛点（有公开证据，✅ 原话已核对，基准日 2026-10-17）

同时开多个 Claude Code / Codex 窗口改同一个仓库，已经是重度用户的日常操作。公开抱怨集中在三件事：

1. **一个 agent 悄悄覆盖另一个的工作，直到合并才发现**（✅ 原话；该提交在 HN 显示为 `[dead]`，如实标注）
   > "Been running multiple Claude Code instances on the same repo ... it works great until two agents end up touching the same file — **one quietly undoes the other's work** and you don't notice until merge time."
   > —— HN item 47324913（提交状态 `[dead]`），https://news.ycombinator.com/item?id=47324913
2. **worktree 工具不自动处理合并冲突**（✅ 原话）
   > "one issue I've seen with other tools doing worktree stuff is they **don't deal with merge conflicts automatically**."
   > —— HN item 48238822（Superset, YC P26），https://news.ycombinator.com/item?id=48238822
3. **没有锁定时，两个 agent 抢同一个任务**（✅ 原话）
   > "**Duplicate work**: two agents would claim the same task when there was no locking."
   > —— HN item 47289444，https://news.ycombinator.com/item?id=47289444
4. **反方观点（必须一并写入，不得只挑支持自己的证据）**（✅ 原话）
   > "Each agent runs in a separate worktree ... The issue you mentioned gets caught during merge conflicts. No different than a 'real' dev team?"
   > —— HN item 47626971，https://news.ycombinator.com/item?id=47626971

**痛点收敛成一句话**：并行写入的损失发生在"覆盖的那一秒"，而现有工作流只能等到"合并的那一刻"才知道；中间这段时间没有任何工具在比对"谁正在改什么"。

**反方观点意味着什么**：如果每个 agent 都在独立 worktree 且最终走人工合并，那么冲突确实会被 git 在合并时拦下——本题的价值只在"提前量"（省掉返工与覆盖损失），**不在"git 拦不住的冲突"**。因此题面不夸大：本工具是**事前预警**，不是安全边界；它不能让错误的合并变正确，只能让覆盖更早被发现。

## 二、任务要求

> **首期范围限定为五个模块**（M1–M5）；文件监听实时模式、CI 前置检查、更多 agent 工具适配留扩展（§2.6）。
> **只读纪律**：全部模块**只读**用户仓库与会话，**不写用户代码、不自动合并、不自动解决冲突、不接管 agent 编排**。
> **数值口径一处定义**：活跃时间窗、严重度分级阈值、符号重叠行数阈值、会话扫描窗口，全部只在 `config/radar.toml`（M1 落定的唯一配置文件）定义一次；报告、基准、文档、README 一律引用，**不得手写第二份数值表**。
> **不写会随实现漂移的硬数字**（测试数 / 文件数 / 输出行数 / 检出率的分母）；确需数字时以末态回填，或注明"合成基准由生成器决定"。
> **合成基准是真值来源**：真实并行冲突样本不足（§1.3），本题的验收主体是 M5 的合成冲突矩阵；任何模块的输出都必须能在该矩阵上被断言。

### 模块 M1：工作区与会话发现

- **输入**：
  - `git worktree list --porcelain`（当前仓库及其 worktree 集合；路径自适应，不硬编码用户名）；
  - agent 会话：Claude Code `~/.claude/projects/**/*.jsonl`（`cwd` / `gitBranch` / 时间戳）、Codex `~/.codex/sessions/**/*.jsonl`（`session_meta.payload.cwd` / 时间戳）；
  - 用户可显式指定 `--repo` / `--claude-root` / `--codex-root` / `--window`。
- **处理**：
  1. 解析 worktree 集合（主工作区 + 各 worktree 的路径、HEAD、分支）；
  2. 扫描会话，抽取 `cwd`、`gitBranch`、会话起止时间、parent/child 关系（区分独立会话与 subagent）；
  3. 按"工作区路径 ↔ 会话 cwd"匹配，建立**"活跃 agent × 工作区 × 时间窗"表**；
  4. **格式版本检测**：按字段指纹识别会话格式版本；不认识的版本**显式报 `unsupported_format` 并列出缺失键**，不得静默产出空表。
- **输出**：`WorkspaceTable{worktrees[], sessions[], active_cells[]}`；每个 cell 记录 agent 类型、会话 id、工作区、时间窗、是否 subagent、parent id。
- **确定性纪律**：同一输入 → 同一排序与同一 cell 集合；子 agent 必须标注 `derived_from`，**不得**与父会话混为独立并行；找不到会话源时显式报错，**不得**伪造空结果（不得退化为 exit 0）。

### 模块 M2：变更意图提取

- **输入**：M1 的活跃会话 + 目标仓库工作区。
- **处理**：
  1. 从会话中解析写文件类工具调用：Claude `Edit` / `Write` / `MultiEdit` 的 `file_path`，Codex `apply_patch` 的文件指令行；
  2. 对每次写操作记录**时间戳、旧文本 `old_string` / 新文本 `new_string`、补丁片段、会话 id、工作区**；
  3. 结合 `git status --porcelain` 与**未提交 diff**（`git diff` / `git diff --cached`）确认磁盘上的真实变更；
  4. 输出"正在改的文件集合"：按 `(工作区, 文件)` 聚合，附"最后写入时间 + 涉及会话 + 改动行区间（可从 diff 得到的部分）"。
- **输出**：`IntentSet{entries[]}`，每条 `entry` 含 `workspace`、`path`、`sessions[]`、`last_write_ts`、`changed_ranges[]`、`evidence`（会话行号 / diff hunk 引用）。
- **确定性纪律**：解析不到 `file_path` 的写操作落 `unknown` 并计入统计，**不得猜测补全**；同一会话同文件多次写入按时间序合并；`replace_all` 或无法定位的编辑**不得**伪造成精确行区间，只能标 `coarse`。

### 模块 M3：三级冲突检测

- **输入**：M1 的 worktree 表 + M2 的意图集合 + 目标仓库 git 对象。
- **检测粒度（由粗到细，逐级给出证据）**：
  1. **文件级**：同一文件在两个**活跃**工作区/会话中被修改 → 报"文件级冲突"，附各会话最后写入时间；
  2. **区块级**：对同文件的两个版本执行 `git merge-tree --write-tree <base> <other>` **无副作用试合并**，解析输出中的冲突路径与冲突块（不写索引、不改工作区）；无法试合并（缺共同祖先等）时降级为文件级并标 `degraded`；
  3. **符号级**：用 Python `ast` 解析**旧版本与新版本**文件，提取函数 / 类 / 方法的**限定名与行区间**，比对两侧改动区间是否落在同一符号或相邻符号内；跨语言（非 Python）首期只做行区间近似并标 `approximate`。
- **输出**：`Conflict{level ∈ {file, block, symbol}, workspace_a, workspace_b, path, symbol?, line_ranges, evidence, severity}`；每条冲突必须能指回 M2 的意图条目与 M3 的证据来源。
- **确定性纪律**：**绝不执行合并、绝不写 git 索引、绝不修改工作区**；`git merge-tree` 只读；AST 解析失败时降级并标 `degraded`，不得抛"无冲突"；同一输入同一次序。

### 模块 M4：预警与处置建议

- **输入**：M3 的冲突清单。
- **处理**：
  1. 按严重度排序：**同一符号被两侧修改 > 同一文件不同符号 > 同文件仅行区间相邻 > 仅文件级同改**（阈值与权重在 `config/radar.toml` 一处定义）；
  2. 每条给出：粒度、文件、符号名、重叠行数、涉及的 agent 与会话 id、最后写入时间、建议（"由更早开始的会话先合并" / "两侧并行改同一符号，需人工裁决" / "仅同文件，可先后提交"）；
  3. 输出 **Markdown 报告**；桌面通知为**可选**（不存在时静默跳过并标注 `notify_unavailable`，不得影响主流程）。
- **输出**：`report.md`（人读）+ `conflicts.json`（机读，供 M5 与 CI 消费）；CLI 退出码语义：`0` = 无冲突、`1` = 有冲突、`2` = 用法错误、`3` = 依赖/环境缺失（如 git 不可用）。
- **确定性纪律**：报告排序稳定、字段稳定；时间一律按会话/文件时间戳原值呈现，**不编造**"预计完成时间"之类的推断；建议文案是**规则模板**，不是模型判断。

### 模块 M5：合成基准（核心交付）

- **输入**：程序化生成的临时 git 仓库 + 合成的 agent 会话日志。
- **场景矩阵（每组都必须植入真值）**：
  1. **同文件不同函数**：两个会话分别改 `alpha.py` 的 `f()` 与 `g()` → 期望判定为**文件级冲突**，符号级不应报同一符号；
  2. **同函数不同行**：两个会话改同一函数的首尾两段 → 期望判定为**符号级冲突**，并给出重叠/相邻行区间；
  3. **整文件覆盖**：一侧 `Write` 覆盖整文件、另一侧局部 `Edit` → 期望判定为**文件级 + 符号级（被覆盖符号）** 冲突；
  4. **subagent 派生**：同一 parent 派生的 subagent 并行 → 必须标注 `derived_from`，**默认不报跨 agent 冲突**（可配置为提示），防止把"自己和自己并行"误报；
  5. **负样本（不应报冲突）**：两个会话改**完全不重叠的文件**、或时间窗不重叠 → 期望**空检出**，用于防误报；
  6. （扩展矩阵项）同文件但两侧改动间隔大于阈值 → 期望按配置判定，测阈值口径。
- **输出**：基准生成器 + 真值文件（每组场景声明"应检出的粒度与对象"）+ 一条命令可复跑的评分命令；断言**检出集合精确匹配**（多报、漏报都算失败）。
- **确定性纪律**：合成仓库使用白名单假项目名/假包名（见 [data/README.md](../data/README.md)），**零真实路径、零真实 session id**；生成器与真值同步产出，**真值不得事后手工补**；同一命令重复运行结果逐字节一致（时间戳等易漂字段固定）。

### 2.6 扩展项（不承诺首期交付）

- **文件监听实时模式**：`watch` 常驻进程，按文件系统事件增量比对（首期只做一次性扫描）；
- **CI 前置检查**：在 PR 前跑同一检测器并以非零退出码拦截（首期只提供 CLI 与 JSON）；
- **更多 agent 工具适配**：首期只覆盖 Claude Code + Codex + git 工作区；Cursor / Aider / 其他 harness 留扩展；
- **跨机器/远端会话**：首期纯本地，不聚合远端。

## 三、提交材料

1. **纯本地 Python CLI**（`pip install .` 或 `python -m` 可调用；零第三方重依赖优先，标准库 `ast` / `json` / `subprocess` 为主）；
   - **交付形态唯一**：命令行程序（console script 与 `python -m` 两条通路），**无图形界面、无打包可执行件、无服务器**；§二 M4 里的"桌面通知"是**可选输出渠道**（缺失时静默跳过并标注 `notify_unavailable`），不是交付形态。
   - **形态的功能验收标准**：上述两条通路在干净环境各自实跑通过——`--version` / `config` / `selftest` 退出码 0，五条业务命令按 §二 声明的退出码语义返回（无冲突 0 / 有冲突 1 / 用法错误 2 / 依赖缺失 3），且人读报告与机读产物可由命令**复现**（同输入双跑逐字节一致）。**空壳不满足验收**：命令存在但只返回 0 或空产物，视为未交付。
2. 五个首期模块的完整实现（发现 / 意图提取 / 三级检测 / 预警 / 合成基准）；
3. **合成冲突矩阵 + 植入真值**：程序化构造并行场景，生成时同步标注"应检出的粒度与对象"，一条命令复现并输出对账结果；
4. **技术报告**：worktree/会话归集口径、`git merge-tree` 试合并的边界、AST 符号区间比对方法、严重度分级口径、隐私设计；
5. **README**：三分钟演示（合成场景 + 本机只读演示）、四级粒度说明、退出码语义、配置项与唯一数值定义位置；
6. **GitHub Release**：源码 zip（附产物）+ **发布留档**（sha256 可复验）。

## 六、边界与非目标

- **不做自动合并 / 不自动解决冲突**：只预警，**绝不**写 git 索引、不执行 merge/rebase、不修改任何代码文件；用户自己决定怎么处置。
- **不接管 agent 编排**：不做任务分配、不启动/停止 agent、不做锁服务；编排器已饱和（§1.2 高星均为编排器），本题只做检测。
- **不修改用户代码**：全链路只读；输出只写 `report.md` / `conflicts.json` 到用户指定目录（默认当前目录）。
- **不承诺覆盖所有 agent 工具**：首期只覆盖 Claude Code + Codex + git 工作区；其他 harness 留扩展，不得在 README 中包装为"通用"。
- **隐私红线**：会话日志含 **prompt 与代码** → **纯本地、零上传、零遥测、不联网**；真实日志、真实路径清单、真实 session id 一律**不入仓**；公开仓库只含合成场景。
- **品牌隔离**：不复制同系列其他项目代码；公开文档不提及任何其他项目的名称与业务领域；本题只描述"并行写入冲突"问题域。
- **首期范围限定**：五个模块（M1–M5）；文件监听、CI 前置、更多 harness、远端聚合留扩展。
- **真实样本不足，验收以合成基准为准**：本机同文件重叠 0 对（§1.3），题面与 README 必须明写"真实并行冲突样本几乎为零，检出能力由合成冲突矩阵断言"；不得用真实样本数包装准确率。
- **反方观点成立的部分必须承认**：独立 worktree + 人工合并会让 git 在合并时拦下冲突（HN 47626971）。本题的价值是**提前量**，不是"git 拦不住"；报告措辞不得声称能防止所有覆盖。
- **不承诺跨版本兼容**：会话格式随 agent 版本演进，解析器以"本机实测字段 + 版本指纹"为依据；不认识的新格式显式报错，不得猜测。
